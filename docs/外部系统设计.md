> **设计目标**：设计一个外部权限管理系统，满足 `docs/RAG系统设计v14.md` 的契约要求，服务 RAG v14 项目的权限管理需要。

## 二、权限服务后端 (Permission Service) 设计

### 2.1 定位

权限服务后端是 RAG v14 系统与 Cerbos PDP 之间的**中间层服务**，负责：

| 职责 | 说明 |
|------|------|
| **ACL/角色绑定/限制的权威存储** | 这些数据不在 RAG 系统，不在 Cerbos PDP，而在此服务 |
| **包装 Cerbos PDP 决策** | 将 ACL 数据注入 Cerbos principal/resource attr，调 PDP 判定 |
| **提供投影面** | prefilter + visibility 端点——基于 ACL 数据预计算，供 RAG 系统高频调用 |
| **提供管理面** | 生命周期端口 (register/link/unlink/retire) + 管理台 CRUD API |
| **发布 VisibilityChanged 事件** | ACL 变更后通知 RAG 系统刷新盖戳 |
| **ctx_token 铸造与验证** | 替 RAG 系统安全传递 credential 到异步 worker |

### 2.2 技术选型建议

| 层 | 选型 | 理由 |
|----|------|------|
| 语言/框架 | **Python (FastAPI)** 或 **Go (Gin)** | Python: 与 RAG 系统技术栈一致，团队可维护；Go: 高性能、低资源、适合高并发投影查询 |
| 数据库 | **PostgreSQL** | 与 RAG 系统相同，运维统一；ACL/角色绑定数据需要事务一致性 |
| PDP | **Cerbos PDP** (已有) | 策略评估引擎，通过 HTTP/gRPC 调用 |
| 事件发布 | **Redis Pub/Sub** 或 **PostgreSQL Outbox** | RAG 系统已用 Redis，保持技术栈一致 |
| 部署 | Docker Compose（开发）/ K8s（生产） | 与 RAG 系统共用基础设施 |

**推荐选型**：Python (FastAPI) + PostgreSQL + Redis Pub/Sub，理由是与 RAG 系统技术栈完全一致，降低运维复杂度。

### 2.3 数据模型

#### 2.3.1 核心表设计

```sql
-- ═══════════════════════════════════════════════════
-- 资源注册表（结构镜像的权威源）
-- ═══════════════════════════════════════════════════
CREATE TABLE resource_registry (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    resource_type VARCHAR(64)  NOT NULL,        -- 'kb' | 'document' | 'directory'
    resource_id   VARCHAR(255) NOT NULL,        -- RAG 系统中的资源 ID
    tenant_id     VARCHAR(255) NOT NULL,        -- 所属租户
    owner         VARCHAR(255) NOT NULL,        -- 'user:xxx' 格式
    retired       BOOLEAN NOT NULL DEFAULT false,
    is_enabled    BOOLEAN NOT NULL DEFAULT true, -- 运营停用标记（不影响 ACL，仅影响检索可见性）
    allow_download BOOLEAN NOT NULL DEFAULT true,-- 是否允许下载（doc:download 判定时检查）
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    
    UNIQUE (resource_type, resource_id)
);

-- ═══════════════════════════════════════════════════
-- 挂载关系表
-- ═══════════════════════════════════════════════════
CREATE TABLE mount_registry (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    doc_id     VARCHAR(255) NOT NULL,
    kb_id      VARCHAR(255) NOT NULL,
    unlinked   BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    
    UNIQUE (doc_id, kb_id)
);

-- ═══════════════════════════════════════════════════
-- ACL 表 (Access Control List) —— 权限授予记录
-- ═══════════════════════════════════════════════════
CREATE TABLE acl_entries (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     VARCHAR(255) NOT NULL,
    principal     VARCHAR(255) NOT NULL,        -- 'user:alice' | 'group:eng' | 'role:viewer'
    resource_type VARCHAR(64)  NOT NULL,        -- 'kb' | 'document'
    resource_id   VARCHAR(255) NOT NULL,        -- 资源 ID
    action        VARCHAR(64)  NOT NULL,        -- 'kb:read' | 'doc:view' | 'doc:download' | ...
    granted_by    VARCHAR(255) NOT NULL,        -- 授予者
    granted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at    TIMESTAMPTZ,                  -- 可选的过期时间
    revoked       BOOLEAN NOT NULL DEFAULT false,
    revoked_at    TIMESTAMPTZ,
    
    -- 一个 principal 对同一资源的同一 action 只应有一条活跃记录
    UNIQUE (principal, resource_type, resource_id, action)
);
CREATE INDEX idx_acl_resource ON acl_entries(resource_type, resource_id) WHERE NOT revoked;
CREATE INDEX idx_acl_principal ON acl_entries(principal) WHERE NOT revoked;
CREATE INDEX idx_acl_tenant ON acl_entries(tenant_id);

-- ═══════════════════════════════════════════════════
-- 角色绑定表
-- ═══════════════════════════════════════════════════
CREATE TABLE role_bindings (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     VARCHAR(255) NOT NULL,
    principal     VARCHAR(255) NOT NULL,        -- 'user:alice' | 'group:eng'
    role          VARCHAR(64)  NOT NULL,        -- 'kb_reader' | 'kb_writer' | 'kb_admin' | 'admin'
    resource_type VARCHAR(64),                  -- 可选：限定到特定资源类型的 KB
    resource_id   VARCHAR(255),                 -- 可选：限定到特定 KB
    granted_by    VARCHAR(255) NOT NULL,
    granted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked       BOOLEAN NOT NULL DEFAULT false,
    revoked_at    TIMESTAMPTZ,
    
    UNIQUE (principal, role, resource_type, COALESCE(resource_id, ''))
);

-- ═══════════════════════════════════════════════════
-- 限制表（封禁/阻断规则）
-- ═══════════════════════════════════════════════════
CREATE TABLE restrictions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id       VARCHAR(255) NOT NULL,
    restriction_type VARCHAR(64) NOT NULL,       -- 'subject_ban' (型一) | 'resource_restriction' (型二)
    principal       VARCHAR(255),                -- 型一：被封禁的主体
    resource_type   VARCHAR(64),                 -- 型二：受限的资源类型
    resource_id     VARCHAR(255),                -- 型二：受限的资源 ID
    reason          TEXT,
    created_by      VARCHAR(255) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    removed         BOOLEAN NOT NULL DEFAULT false,
    removed_at      TIMESTAMPTZ,
    
    -- 型一封禁：principal 必须非空
    -- 型二限制：resource_type + resource_id 必须非空
    CONSTRAINT ck_restriction_type CHECK (
        (restriction_type = 'subject_ban' AND principal IS NOT NULL) OR
        (restriction_type = 'resource_restriction' AND resource_type IS NOT NULL)
    )
);

-- ═══════════════════════════════════════════════════
-- 变更事件日志表（用于对账 + 审计）
-- ═══════════════════════════════════════════════════
CREATE TABLE permission_changes (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type    VARCHAR(128) NOT NULL,        -- 'ACL_GRANTED' | 'ACL_REVOKED' | 'ROLE_BOUND' | 'RESTRICTION_ADDED' | ...
    resource_type VARCHAR(64),
    resource_id   VARCHAR(255),
    kb_id         VARCHAR(255),                 -- 用于 KB 粒度事件展开
    tenant_id     VARCHAR(255) NOT NULL,
    change_detail JSONB NOT NULL,               -- 变更详情
    version       BIGINT NOT NULL,              -- 全局单调递增版本号
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_pc_resource ON permission_changes(resource_type, resource_id);
CREATE INDEX idx_pc_kb ON permission_changes(kb_id);
CREATE INDEX idx_pc_version ON permission_changes(version);
```

### 2.4 API 设计

#### 2.4.1 决策面 API（RAG 系统 P-AUTHC 调用）

```
┌─────────────────────────────────────────────────────────────────────┐
│ POST /v1/check                                                      │
├─────────────────────────────────────────────────────────────────────┤
│ 调用方: P-AUTHC check()                                             │
│ Client-ID: interactive-backend                                      │
│                                                                     │
│ Request:                                                            │
│   {                                                                 │
│     "request_id": "abc123...",                                      │
│     "credential": "<JWT raw>",                                      │
│     "action": "kb:write",                                           │
│     "resource": {"type": "kb", "id": "kb-uuid"},                    │
│     "channel": {"kb": "kb-uuid"}   // 通道类动词必带                 │
│   }                                                                 │
│                                                                     │
│ 后端处理:                                                           │
│   1. 从 JWT 解析 principal (user_id, roles, groups)                 │
│   2. 查询 ACL 表: 该 principal 是否有此 action?                      │
│   3. 查询 restrictions 表: 该主体/资源是否被封禁?                    │
│   4. 构造 Cerbos principal (含 resolved permissions)                │
│   5. 调用 Cerbos /api/check/resources                               │
│   6. 三态映射: EFFECT_ALLOW→allow, DENY→deny, 其他→indeterminate    │
│                                                                     │
│ Response:                                                           │
│   {                                                                 │
│     "decision": "allow" | "deny" | "indeterminate",                 │
│     "decision_id": "cerbos-call-id-xxx",                            │
│     "reasons": [],                                                  │
│     "obligations": {}                                               │
│   }                                                                 │
│                                                                     │
│ 性能目标: p95 < 50ms                                                 │
│ 限流: 每 client 1000 req/s                                          │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ POST /v1/filter                                                      │
├─────────────────────────────────────────────────────────────────────┤
│ 调用方: P-AUTHC filter_items() (仅 strict KB, 层3)                   │
│ Client-ID: retrieval                                                 │
│                                                                     │
│ Request:                                                            │
│   {                                                                 │
│     "request_id": "...",                                            │
│     "credential": "<JWT raw 或 ctx_token>",                         │
│     "items": [                                                      │
│       {"resource_type": "document", "resource_id": "doc-1",         │
│        "channel": {"kb": "kb-uuid"}},                               │
│       ...                                                           │
│     ]  // ≤200 条                                                   │
│   }                                                                 │
│                                                                     │
│ 后端处理:                                                           │
│   对每条 item 执行 doc:retrieve 判定                                  │
│   → 批量调 Cerbos，单次往返                                          │
│                                                                     │
│ Response:                                                           │
│   {                                                                 │
│     "allowed": ["doc-1", "doc-3"],                                  │
│     "denied":  ["doc-2"],                                           │
│     "decision_id": "..."                                            │
│   }                                                                 │
│                                                                     │
│ 约束: 单批 ≤200; 超时/失败 → RAG 侧整批 deny; 永久禁止缓存          │
└─────────────────────────────────────────────────────────────────────┘
```

#### 2.4.2 投影面 API

```
┌─────────────────────────────────────────────────────────────────────┐
│ GET /v1/prefilter?credential=<JWT>                                  │
├─────────────────────────────────────────────────────────────────────┤
│ 调用方: P-AUTHC get_prefilter() (每次检索前)                         │
│ Client-ID: retrieval                                                 │
│                                                                     │
│ 后端处理:                                                           │
│   1. 从 JWT 解析 principal                                          │
│   2. 查询 restrictions: 该主体是否被型一封禁?                          │
│      → 是: 返回 {suspended: true}                                   │
│   3. 查询 ACL + role_bindings:                                      │
│      该 principal 在哪些 KB 上有 kb:read 或更强权限?                  │
│   4. 查询 resource_registry: 过滤 retired=false 的资源               │
│   5. 计算 kbs (允许列表) 和 excluded_kbs (型二封禁的资源)            │
│                                                                     │
│ Response:                                                           │
│   {                                                                 │
│     "kbs": ["kb-uuid-1", "kb-uuid-3"],                              │
│     "excluded_kbs": [],                                             │
│     "tenant_wide_read": false,                                      │
│     "policy_version": "v12345",          // = 全局版本号              │
│     "ttl_s": 60,                        // 请求内缓存 TTL            │
│     "expires_at": "2026-07-30T12:01:00Z"                            │
│   }                                                                 │
│                                                                     │
│ 或 (型一封禁):                                                       │
│   {                                                                 │
│     "suspended": true,                                              │
│     "reason": "subject_banned"                                      │
│   }                                                                 │
│                                                                     │
│ 性能目标: p95 < 30ms (高频调用)                                      │
│ 缓存: RAG 侧请求内缓存 (不跨请求)，TTL ≤60s                          │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ POST /v1/visibility                                                  │
├─────────────────────────────────────────────────────────────────────┤
│ 调用方: B-INGEST 盖戳管道 (stamp_channel_task)                       │
│ Client-ID: ingest (无主体入参)                                       │
│                                                                     │
│ Request:                                                            │
│   {                                                                 │
│     "tenant": "tenant-dev",                                         │
│     "doc_id": "doc-uuid",                                           │
│     "channel": {"kb": "kb-uuid"}                                    │
│   }                                                                 │
│                                                                     │
│ 后端处理:                                                           │
│   1. 查 mount_registry: 挂载是否存在? 是否已 unlinked?               │
│      → unlinked: 返回 {unmounted: true}                             │
│   2. 查 resource_registry: doc/kb 是否 retired?                     │
│      → retired: 返回 {unmounted: true}                              │
│   3. 查 ACL + role_bindings:                                        │
│      哪些 principal 对此 (doc,kb) 有 doc:retrieve 权限?              │
│      → 计算 allow_stamps 列表                                       │
│   4. 查 restrictions: 哪些 principal 被禁止访问?                     │
│      → 计算 deny_stamps 列表                                        │
│                                                                     │
│ Response:                                                           │
│   {                                                                 │
│     "allow_stamps": ["user:*", "group:eng", "user:bob"],            │
│     "deny_stamps":  ["user:mallory"],                               │
│     "version": 12345,                      // = 全局权限版本号       │
│     "unmounted": false                                              │
│   }                                                                 │
│                                                                     │
│ 关键约束:                                                            │
│  • allow_stamps/deny_stamps 只含原始主体，禁止展开成员               │
│  • version 用于 B-INGEST 版本单调性检查                               │
│  • 此端点无主体入参 — 返回的是该资源的"可见性投影"                   │
│  • 被限流(429) → 返回 Retry-After 头                                │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│ POST /v1/context                                                     │
├─────────────────────────────────────────────────────────────────────┤
│ 调用方: P-AUTHC mint_ctx_token()                                     │
│ Client-ID: interactive-backend                                       │
│                                                                     │
│ Request:                                                            │
│   {                                                                 │
│     "request_id": "...",                                            │
│     "credential": "<JWT raw>",                                      │
│     "audience": "retrieval-worker",                                 │
│     "ttl_s": 600                                                    │
│   }                                                                 │
│                                                                     │
│ 后端处理:                                                           │
│   将 credential + audience + iat + exp 打包为签名 token              │
│   (HMAC-SHA256 或 JWT 自签)                                          │
│                                                                     │
│ Response:                                                           │
│   {                                                                 │
│     "ctx_token": "ctx.eyJjcmVkZW50aWFsIjoi...xyz",                  │
│     "expires_at": "2026-07-30T12:10:00Z"                            │
│   }                                                                 │
│                                                                     │
│ 约束: ttl_s ≤ 600; audience 必须校验; 过期即失效                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 2.4.3 管理面 API — 生命周期端口（RAG 系统 B-DOC 调用）

```
┌──────────────────────────────────────────────────────────────────────┐
│ POST /v1/resources/register                                          │
├──────────────────────────────────────────────────────────────────────┤
│ 调用方: B-DOC (创建 document / 创建 KB 时)                            │
│                                                                      │
│ Request:                                                             │
│   {                                                                  │
│     "resource_type": "kb",                                           │
│     "resource_id": "kb-uuid",                                        │
│     "owner": "user:admin",                                           │
│     "tenant_id": "tenant-dev",                                       │
│     "idempotency_key": "reg-kb-kb-uuid-ts123"  // 必带               │
│   }                                                                  │
│                                                                      │
│ Response (200):                                                      │
│   { "change_id": "...", "result": "created" | "noop" }               │
│                                                                      │
│ Response (409):                                                      │
│   { "error": "idempotency_conflict",                                 │
│     "message": "same key, different payload" }                       │
│                                                                      │
│ 调用纪律:                                                             │
│  • idempotency_key 格式: {facade}-{tenant}-{resource_id}-{schema_v}  │
│  • 禁止时间戳/随机数/UUID                                            │

│  • RAG 侧调用失败 → 回滚本地事务                                      │
└──────────────────────────────────────────────────────────────────────┘

  请求体：{ resource_type, resource_id, doc_id, kb_id, tenant_id, idempotency_key, owner? }
  必填字段：resource_type, resource_id, doc_id, kb_id, tenant_id, idempotency_key
  幂等键格式：{facade}-{tenant_id}-{resource_id}-{kb_id}-{schema_version}

  请求体：{ resource_type, resource_id, doc_id, kb_id, tenant_id, idempotency_key, owner? }
  必填字段同上
POST /v1/resources/retire   -- 资源退役 (resource_type, resource_id)
  请求体：{ resource_type, resource_id, tenant_id, idempotency_key, owner? }
  必填字段：resource_type, resource_id, tenant_id, idempotency_key
    ↑ 四个端点的请求/响应格式与 register 同构，均需 tenant_id 和 idempotency_key

### 2.5 核心业务流程

#### 2.5.1 权限判定 (check)

```
P-AUTHC ──POST /v1/check──► 权限服务后端
                                │
                                │ 1. 解析 JWT → principal
                                │ 2. 查询 ACL + role_bindings + restrictions
                                │    → 构建 Cerbos principal 的 attr.granted_actions
                                │ 3. 查询 resource_registry → 构建 Cerbos resource 的 attr
                                │ 4. POST Cerbos /api/check/resources
                                │ 5. 映射 Cerbos verdict → 三态
                                │
                                ◄── {decision, decision_id, reasons}
```

#### 2.5.2 可见性投影 (visibility)

```
B-INGEST ──POST /v1/visibility──► 权限服务后端
                                      │
                                      │ 1. 查 mount_registry → unlinked?
                                      │ 2. 查 resource_registry → retired?
                                      │ 3. 查 ACL: 哪些 principal 对该 (doc,kb) 有 doc:retrieve?
                                      │    → allow_stamps 列表
                                      │ 4. 查 restrictions: 哪些 principal 被禁止?
                                      │    → deny_stamps 列表
                                      │ 5. 取当前全局版本号 → version
                                      │
                                      ◄── {allow_stamps, deny_stamps, version, unmounted}
```

#### 2.5.3 权限变更 → 事件发布

```
管理台 ──POST /api/v1/acl/grant──► 权限服务后端
                                       │
                                       │ 1. INSERT acl_entries
                                       │ 2. 递增 global_permission_version
                                       │ 3. INSERT permission_changes (version=N)
                                       │ 4. 发布 Redis Pub/Sub:
                                       │    channel: "visibility_changed"
                                       │    payload: {event_type, resource_type, resource_id,
                                       │               kb_id?, tenant_id, version, change_detail}
                                       │
                                       ▼
                                  Redis Pub/Sub "visibility_changed"
                                       │
                                       ▼
                                  P-AUTHC (visibility_events.py 订阅)
                                       │
                                       ▼
                                  B-INGEST stamp_channel_task
```

### 2.6 与 RAG 系统当前实现的对照

当前 RAG 系统 `cerbos_client.py` 中的实现方式 vs 外部权限服务：

| 功能 | 当前实现 (开发模式) | 外部权限服务 (生产模式) |
|------|-------------------|----------------------|
| **check** | 直接调用 Cerbos HTTP API，principal.granted_actions 从本地 resource_registry 反查 | 调用权限服务后端 `/v1/check`，ACL 数据由权限服务管理 |
| **check_batch** | 直接调用 Cerbos /api/check/resources 批量 | 同上，经权限服务后端 |
| **filter_items** | 直接调用 Cerbos，逐 200 条分批 | 调用权限服务后端 `/v1/filter` |
| **get_prefilter** | 查本地 DB knowledge_bases → Cerbos 批量 check kb:read | 调用权限服务后端 `GET /v1/prefilter` |
| **get_visibility** | 查本地 mirror 表 (resource_registry + mount_registry + document_kb_mounts) | 调用权限服务后端 `POST /v1/visibility` |
| **mint_ctx_token** | 本地 HMAC-SHA256 自签 | 调用权限服务后端 `POST /v1/context` |
| **register/link/unlink/retire** | 写本地 mirror 表 (resource_registry / mount_registry) | 调用权限服务后端对应端点 |
| **ACL 管理** | 无（开发模式: owner = full access） | 管理台 → 权限服务后端 API |
| **VisibilityChanged** | 本地 visibility_events.py 轮询 mount_registry | 权限服务 Redis Pub/Sub → P-AUTHC 订阅 |

**迁移策略**：`cerbos_client.py` 中的 `CerbosClient` 类改造为 HTTP 客户端，将当前直接操作本地 DB 的逻辑替换为对权限服务后端的 HTTP 调用。P-AUTHC 模块 (`authz.py`) 的接口签名不变——这是防腐层的价值。

### 3.1 定位

管理台是权限管理员使用的 Web 应用。RAG v14 前端通过 `ADMIN_CONSOLE_URL` 环境变量配置的跳转链接指向管理台。

**推荐**：Next.js 14 + shadcn/ui + Zustand，与 RAG 前端保持技术栈一致。如有成熟的 Ant Design Pro 权限管理模板，也可优先复用。

这样管理台可以展示用户/组列表而无需每次调 Keycloak API，且用户/组数据在管理台的权限授予 Dialog 中可作为选项。

│ 1. 幂等去重 (event_id)       │
│ 2. 如果是 KB 粒度:            │
│    expand_visibility_changed_ │
│    task(kb_id)               │
│    → 分页查本地               │
│      document_kb_mounts      │
│    → 各 (doc, kb) 提交       │
│      stamp_channel_task      │
│ 3. 如果是文档粒度:            │
│    直接提交 stamp_channel_   │
│    task(doc_id, kb_id)       │
└────────────┬─────────────────┘
             │
             ▼
┌──────────────────────────────┐
│ B-INGEST stamp_channel_task  │
│ POST /v1/visibility          │
│ → upsert Milvus chunk stamps │
└──────────────────────────────┘
```

### 5.2 事件可靠性保证

| 保证 | 实现 |
|------|------|
| **至少一次投递** | Redis Pub/Sub + 消费者 ack 机制 (或 Redis Stream) |
| **幂等消费** | 消费者按 event_id 去重 |
| **事件持久化** | permission_changes 表 (PostgreSQL) 持久化所有变更 |
| **事件重放** | 消费者可从指定 version 开始补消费 |
| **对账兜底** | RAG 侧定期对账 (stamp_drift/orphan_stamp/mirror_gap) |

## 七、迁移路径：从本地镜像到外部服务

### 7.1 当前状态

RAG 系统的 `cerbos_client.py` 使用本地 PostgreSQL 表 (`resource_registry`, `mount_registry`) 作为资源镜像，并直接调用 Cerbos PDP HTTP API。这是**开发模式**的实现。

### 7.2 迁移阶段

```
阶段 0: 开发模式 (当前)
  cerbos_client.py
  ├── 决策面: 直接调 Cerbos HTTP API ✅
  ├── 投影面: 本地 DB 查询 ✅
  └── 管理面: 本地 DB INSERT/UPDATE ✅

阶段 1: 权限服务后端上线
  1. 部署 permission-service + 数据库
  2. 迁移 resource_registry / mount_registry 数据到权限服务
  3. cerbos_client.py 改为 HTTP 客户端:
     ├── 决策面: 调 permission-service /v1/check 等
     ├── 投影面: 调 permission-service /v1/prefilter, /v1/visibility
     └── 管理面: 调 permission-service /v1/resources/register 等
  4. 引入功能开关: AUTHZ_SERVICE_MODE=local|remote
     (local: 当前实现; remote: 调外部服务)

阶段 2: 管理台上线
  1. 部署 admin-console
  2. 配置 RAG 系统 .env: ADMIN_CONSOLE_URL=http://192.168.1.127:3002
  3. 在管理台中配置初始权限:
     - 将现有 owner → 转换为 ACL entries
     - 将 system_admin → 绑定 admin 派生角色
  4. 验证: RAG 前端跳转链接全部指向管理台

阶段 3: 事件系统对接
  1. permission-service 发布 VisibilityChanged 到 Redis Pub/Sub
  2. RAG P-AUTHC 订阅 Redis Pub/Sub (替换当前本地轮询)
  3. 验证: 权限变更 → 盖戳自动刷新

阶段 4: 生产加固
  1. 关闭 AUTHZ_SERVICE_MODE=local，强制走 remote
  2. 配置熔断/限流/重试策略
  3. 跑联合契约测试 J-1~J-20
  4. 监控指标: authz_call_duration_seconds, authz_call_failed_total
```

> **总结**：外部系统由权限服务后端 (Python/FastAPI) + 管理台前端 (Next.js) + Cerbos PDP + Keycloak 四方组成。权限服务后端是 ACL/角色绑定/限制的权威存储和 Cerbos PDP 的适配层，提供 RAG 系统所需的全部 5 个决策/投影端点和 4 个生命周期端口。管理台前端是权限管理员的操作界面，RAG 系统通过 `ADMIN_CONSOLE_URL` 跳转进入。迁移路径从当前的本地 DB 镜像 (cerbos_client.py) 通过 `AUTHZ_SERVICE_MODE` 开关逐步切换到外部服务，接口签名保持不变（防腐层的价值）。
