# 权限管理系统架构设计

> **基于**：`docs/RAG系统设计v14.md`（系统设计）、`docs/frontend-design.md`（前端架构设计）、项目代码实际实现
>
> **核心原则（来自设计文档 §0.2.1）**：
> - **本系统零权限判定**——所有授权决策由外部权限服务（Cerbos PDP）完成
> - **授权管理（授予/回收权限）不在本系统**——管理台直连权限服务；本系统 UI 至多提供跳转入口
> - **任何模块不得越过 P-AUTHC 直接调用权限服务 HTTP 端点**

## 一、权限系统全景架构

### 四方职责划分

| 参与方 | 角色 | 职责 | 本系统如何交互 |
|--------|------|------|---------------|
| **IdP（Keycloak）** | 身份源 | 用户/组/角色管理、JWT 签发、SSO | 前端跳转登录；后端本地校签 JWT |
| **权限服务（Cerbos PDP）** | 决策权威 | 策略评估、五端点决策面、投影面、管理面 | **仅通过 P-AUTHC** 调用五端点 |
| **管理台（Admin Console）** | 授权管理 | 角色绑定、权限授予/回收、限制管理、审计查询 | 前端提供跳转链接，**不内嵌** |
| **RAG 本系统** | 权限消费 | 权限拦截（PEP）、权限注入检索、UI 条件渲染 | — |

## 二、权限模型

### 2.1 动词目录（16 个 action，权威定义见上游契约 §4）

```
资源: kb（知识库）          资源: document（文档）
─────────────────────      ─────────────────────────
kb:read      读取           doc:view       只读查看
kb:write     写入           doc:download   下载
kb:manage    管理           doc:retrieve   检索（仅 /v1/filter）
kb:grant     授权           doc:unmount    从 KB 移除
                            doc:purge      彻底删除
                            doc:share      分享
```

**特殊约束**：
- `doc:retrieve` 只能走 `/v1/filter`，禁止走 `/v1/check`
- 通道类动词（`doc:retrieve`、`doc:unmount`）必须带 `channel.kb`

### 2.2 角色层级（Cerbos Derived Roles）

```
system_admin ──→ admin（超级管理员，无条件 allow）
user ──→ kb_reader（需 granted_actions 中有 "read"）
     ──→ kb_writer（需 granted_actions 中有 "write"）
     ──→ kb_admin（需 granted_actions 中有 "manage"）
```

**角色授予机制（v14 §6A.1 管理面）**：
- `granted_actions` 从 JWT claims 的 `granted_actions` 字段读取，或通过 resource_registry 反查
- 当前开发模式：resource_registry 中 owner 为当前用户的资源 → 授予 full access
- 生产模式：通过外部管理台进行角色绑定，写入权限服务

### 2.3 准入矩阵（哪个动作需要哪个角色）

| 动作 | kb_reader | kb_writer | kb_admin | admin | 资源条件 |
|------|-----------|-----------|----------|-------|---------|
| `kb:read` | ✅ | ✅ | ✅ | ✅ | retired=false |
| `kb:write` | — | ✅ | ✅ | ✅ | retired=false, status≠reindexing |
| `kb:manage` | — | — | ✅ | ✅ | — |
| `kb:grant` | — | — | — | ✅ | — |
| `doc:view` | ✅ | ✅ | ✅ | ✅ | is_enabled=true, retired=false |
| `doc:download` | ✅ | ✅ | ✅ | ✅ | is_enabled=true, retired=false, allow_download=true |
| `doc:retrieve` | ✅ | ✅ | ✅ | ✅ | is_enabled=true, retired=false |
| `doc:unmount` | — | ✅ | ✅ | ✅ | retired=false |
| `doc:purge` | — | — | ✅ | ✅ | retired=false |
| `doc:share` | — | — | — | ✅ | — |

## 三、权限数据流

### 3.1 认证流（用户身份获取）

```
浏览器                           RAG 后端                      IdP(Keycloak)
  │                                │                              │
  │  开发模式                       │                              │
  │  POST /api/v1/auth/dev-login   │                              │
  │  {username, tenant, role}      │                              │
  │ ──────────────────────────────►│                              │
  │                                │ 自签 RS256 JWT               │
  │  ◄─────────────────────────────│ {sub, tenant, roles, exp}    │
  │                                │                              │
  │  生产模式                       │                              │
  │  跳转 IdP 登录页                │                              │
  │ ──────────────────────────────────────────────────────────────►│
  │  ◄──────────────────────────────────────────────────────────────│ 回调 /auth/callback?code=xxx
  │                                │                              │
  │  POST /api/v1/auth/token       │                              │
  │  {code}                        │                              │
  │ ──────────────────────────────►│                              │
  │                                │ 换取 JWT + refresh_token     │
  │  ◄─────────────────────────────│                              │
```

### 3.2 授权流（权限判定）

```
API 请求进入
    │
    ▼
┌──────────────┐
│ AuthMiddleware│ ← JWT 本地校签（快速失败）
│ build_context │   构建 RequestContext（含 credential, principals）
└──────┬───────┘
       │
       ▼
┌──────────────────┐
│ require_permission│ ← 路由级依赖注入
│ (action, res)     │   → POST /v1/check（Cerbos）
│                   │   → allow → 执行业务
│                   │   → deny → 403（与 not-found 同型文案）
│                   │   → indeterminate → 503 + 告警
│                   │   → 超时/不可达 → 503 + 熔断器
└──────┬───────────┘
       │
       ▼
  业务逻辑执行
```

### 3.3 检索权限流（三层链路）

```
检索请求进入
    │
    ▼
┌────────────────┐
│ 层 1: prefilter │ → GET /v1/prefilter
│ 编译注入         │   → 六条件 MetadataFilter
│                 │   → suspended=true → 跳过检索
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│ 层 2: 过采样    │ → k × 1.5 过采样
│ + 补检索        │   → 不足时收窄候选通道补检索
│                 │   → MetadataFilter 不变
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│ 层 3: 逐条复核  │ → POST /v1/filter（仅 strict=true KB）
│ (filter_items)  │   → 按 (doc_id,kb_id) 去重
│                 │   → ≤200/批，失败整批 deny
│                 │   → 永久禁止缓存
└──────┬─────────┘
       │
       ▼
  生成合成 + 返回
```

### 3.4 盖戳流（可见性投影）

```
┌────────────────────┐
│ 触发源（三选一）     │
│ ① 摄入完成          │
│ ② VisibilityChanged │
│ ③ 对账补偿          │
└──────┬─────────────┘
       │ 汇聚到 stamp_channel_task
       ▼
┌────────────────────┐
│ POST /v1/visibility │ → 取当前 (doc,kb) 的可见性戳记
│ (x-client-id:ingest)│   → allow_stamps, deny_stamps, version
└──────┬─────────────┘
       │
       ▼
┌────────────────────┐
│ 六条纪律            │
│ ① 失败不落盘        │
│ ② unmounted 清空    │
│ ③ 版本单调性        │
│ ④ 分批 upsert(500)  │
│ ⑤ 游标断点续跑      │
│ ⑥ 审计 fail-open    │
└──────┬─────────────┘
       │
       ▼
 Milvus chunk payload 更新：
   allow_stamps / deny_stamps / vis_version
```

### 3.5 生命周期流（资源登记/挂载/回收）

```
B-DOC 写路径（创建/挂载/删除）
    │
    ▼
┌────────────────────────────┐
│ 同步调权限服务生命周期端口   │
│ ★ 先服务，成功后提交本地事务 │
│ 失败 → 回滚本地事务         │
│                            │
│ register_resource ─────────│→ INSERT resource_registry
│ link_resource ─────────────│→ INSERT mount_registry
│ unlink_resource ───────────│→ UPDATE mount_registry SET unlinked=true
│ retire_resource ───────────│→ UPDATE resource_registry SET retired=true
│                            │    + 级联清理 mount_registry
└────────────────────────────┘
```

## 八、安全边界与红线

### 8.1 本系统红线（来自 §0.2）

1. **零权限判定**：不存在任何本地 `if owner then allow` 逻辑
2. **P-AUTHC 是唯一出口**：所有权限服务调用必须经过 P-AUTHC
3. **credential 不外泄**：JWT 原文不出现在日志、trace、审计 payload、任务参数中
4. **fail-closed 全覆盖**：权限服务不可达 → 全部拒绝，不允许降级为"无过滤查询"
5. **存在性三通道**：deny 与 "未找到足够信息" 使用完全相同的用户文案
6. **事后过滤禁令**：不允许先查全量再应用层过滤
7. **不缓存决策结果**：`/v1/filter` 永久禁缓存；`/v1/check` 缓存默认关闭

### 8.2 跨系统边界

```
        本系统边界
  ┌──────────────────────┐
  │                      │
  │  P-AUTHC ──────HTTP──┼──→ 权限服务 (Cerbos PDP)
  │                      │
  │  resource_registry   │     ← 本系统维护的资源镜像
  │  mount_registry      │     ← 与权限服务结构镜像保持一致
  │                      │
  │  前端 ──跳转链接─────┼──→ 管理台 (Admin Console)
  │                      │
  └──────────────────────┘
  
  ★ 权限服务 /readyz 不纳入本系统 health check
  ★ 结构镜像对账定期比对 resource_registry/mount_registry 与权限服务侧
  ★ ctx_token ttl ≤ 600s，过期即任务失败
```

> **总结一句话**：本 RAG 系统是权限的**消费方**和**执行方**，不是权限的**管理方**。所有授权决策由外部 Cerbos PDP 完成，所有授权管理（授予/回收/角色绑定）由外部管理台完成。本系统的职责是：正确消费权限决策（P-AUTHC 五端点）、正确执行权限过滤（三层检索 + 盖戳管道）、正确传递权限上下文（JWT → ctx_token → prefilter → MetadataFilter）、以及在 UI 上提供到管理台的跳转入口和基本的权限感知渲染。
