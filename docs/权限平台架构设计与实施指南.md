# 独立权限平台架构设计与实施指南

> 类型：技术设计与经验总结（架构设计 + 权限设计方法 + 设计注意事项 + 实施踩坑清单）
> 适用：将本平台作为独立、多项目、多租户的授权中台落地或二次开发。
> 关联文档：`permission_model_v2.md`（权限模型规范）、`rag_permission_service_diagnose_v14.md`~`v20.md`
> （诊断与整改记录，缺陷编号 F/G/D/OBS 的完整验证过程）、`readme.md`（部署与使用）。

## 第一部分 · 架构设计

### 1. 定位与职责边界

本平台是一个**独立的授权中台**：集中管理"谁能对什么资源做什么"，并为多个业务系统（项目）
提供统一的判定、投影、资源镜像与管理能力。业务系统只作为**权限消费方**，自身不做任何授权判定。

四方协作，各自单一职责：

| 角色 | 组件 | 只负责 |
| --- | --- | --- |
| 身份源 IdP | Keycloak | 用户/组/身份角色、JWT 签发；不存业务授权 |
| 决策引擎 PDP | Cerbos | 按策略文件评估请求 → allow/deny；不存事实数据 |
| 权限服务 | FastAPI 后端 | 组装事实数据 + 调 Cerbos + 事件/审计/资源镜像；不自己判权 |
| 管理台 | Admin Console | 授予/回收/绑定/封禁/策略/审计的操作界面；不判权 |

**红线**：任何业务模块不得越过权限服务直接调用 Cerbos；授权决策只有 Cerbos 一条路径。

### 2. 组件与调用关系

```
业务系统(消费方) ──X-Api-Key+X-Client-Id──▶ 权限服务 /v1/*  ──gRPC/HTTP──▶ Cerbos PDP
                                              │  ▲                          ▲
  管理台 ──Bearer JWT──▶ 权限服务 /api/v1/*    │  │ 组装事实                   │ 读策略文件
                                              ▼  │                          │
                                          PostgreSQL(事实) ◀── 同一份 ──▶ cerbos/policies/*.yaml(规则)
                                              │
                                          Redis(事件/缓存)  ◀── Outbox 双通道发布变更
        Keycloak(IdP) ──JWT 公钥校签 / 定时同步 user_cache──▶ 权限服务
```

- **两类入口**：`/v1/*` 外部系统鉴权（API Key + Client-Id，中间件解析出 project_id）；
  `/api/v1/*` 管理台鉴权（Bearer JWT，`get_current_admin`）。
- **判定期数据三源**：事实（授权记录）来自 PostgreSQL，规则来自策略文件，决策由 Cerbos。
- **策略文件双消费者**：Cerbos 直接加载判定；权限服务解析同一份文件用于展示（角色权限矩阵）。
  两者视图必须一致，靠"文件是唯一权威"保证。

### 3. 部署拓扑与端口

| 服务 | 容器端口 | 宿主端口 | 说明 |
| --- | --- | --- | --- |
| permission-service | 8080 | 18080 | FastAPI 后端 |
| admin-console | 3000 | 3002 | 管理台前端 |
| perm-postgres | 5432 | 25433 | 事实存储 |
| perm-redis | 6379 | 16380 | 事件/缓存 |
| cerbos | 3592/3593 | 13592/13593 | PDP（HTTP/gRPC）|
| keycloak | 8080 | 8080 | IdP（独立 compose）|
| （观测栈，独立编排）| — | 3000/4317/4318 | OTel Collector→Tempo/Loki→Grafana |

Cerbos 与权限服务挂载**同一份** `cerbos/policies`；`watchForChanges` 开启，策略写入后 PDP 自动
重载，无需重启。

## 第二部分 · 权限应该如何设计

### 4. 设计底线（单一数据源）

> 策略文件描述**结构（规则）**，DB 记录**事实**，Cerbos 做**决策**。
> 没有一类数据同时存在于两个地方，没有第二条判断路径，没有需要手动同步的状态。

落到具体：

| 数据 | 唯一落点 | 明确**不**放的地方 |
| --- | --- | --- |
| "角色能做什么"（role→action 规则）| Cerbos 策略 YAML | DB（`role_definitions` 无 `permissions` 列）|
| "谁被授了什么"（绑定/ACL/封禁）| DB 事实表 | 策略文件（策略不含 user_id）|
| "某次请求放不放行" | Cerbos 运行时判定 | 后端本地不做二次推断 |
| 角色档案（名称/激活角色/归属）| DB `role_definitions`（仅索引）| 不记 `policy_synced` 同步态 |

**为什么**：任何"双写"都会产生需要同步的状态，最终必然分叉。把每类数据钉在唯一位置，
判定时现读现算，是本平台所有正确性的根。

### 5. 三层授权模型

```
Layer 1 平台层  policies/platform/platform.yaml
  "你有没有资格进这个管理功能模块？"
  认 Keycloak 角色 + 平台角色绑定 + 按功能的委托 ACL；不 import 任何项目派生角色。

Layer 2 项目权限数据层  policies/platform/project_permission.yaml
  "进门后你能操作这个项目的哪类权限数据？"
  认 granted_actions[project_id]，全局唯一文件，所有项目共用。

Layer 3 项目业务层  policies/{project}/…
  "在这个项目里你能对这个资源做什么？"
  三路并行：ABAC（项目级/KB 级）+ ACL 用户级 + ACL 角色级；任一命中即 ALLOW，全未命中隐式 DENY。
```

目录布局：

```
cerbos/policies/
├── platform/resource_policies/{platform.yaml, project_permission.yaml}   ← 全局唯一，不随项目增减
└── {project_id}/{derived_roles/*.yaml, resource_policies/*.yaml, .versions/}  ← 每项目一目录
```

### 6. 模块分级（平台专属 vs 项目内）

管理台功能模块必须先分级，这是越权防护的地基：

| 分级 | 模块 | 谁可见/可管 |
| --- | --- | --- |
| 平台专属 | 项目管理 project_mgmt、租户管理 tenant_mgmt、系统设置 settings、用户与组 user_mgmt | 仅平台管理员（system_admin / platform_admin）|
| 项目内（7 个）| 资源 resource_mgmt、角色 role_mgmt、权限 permission_mgmt、封禁 restriction_mgmt、策略 policy_mgmt、审计 audit_mgmt、模拟 playground | 项目管理员读写；项目查看者只读子集（资源/角色）|
| 通用 | dashboard | 登录首页，所有身份只读 |

项目基础设施（API Key / client / audience）在语义上属 project_mgmt，但可下放为"项目管理员对
**本项目**自助"。

### 7. 两种授权模型（按项目选一）

| 模型 | 适用 | 机制 | 参考项目 |
| --- | --- | --- | --- |
| 属性注入式（ABAC）| 授权随资源实例/通道动态变化（如知识库、文档）| 派生角色条件读 `request.principal.attr.granted_actions`，后端从 DB 查授权注入 | rag-v14（kb/document）|
| 静态角色式（RBAC）| 授权按固定岗位（如 OA 的员工/经理/HR）| Keycloak 建 Realm 角色 + 派生角色 parentRoles + 属性条件 | demo2（oa_roles）|

资源类型与动作**由项目自己定义**（写在该项目策略里），平台不内置业务动作。资源类型名**全平台
唯一**，务必加项目前缀。

### 8. 资源与主体

- **主体展开**：`principal.roles` = JWT 角色 ∪ 平台角色绑定（project_id IS NULL）∪ 由
  `project_members.role` 合成的项目角色（project_admin / project_member）∪ `user`。
- **资源属性**：判定期从 `resource_registry` 取 `retired/is_enabled/allow_download/owner/tenant_id`，
  从请求取通道属性（kb_id），从 `acl_entries` 取 acl/role_acl，注入 `resource.attr`。策略文件里
  不含任何 user_id 或角色名。

### 9. 租户与项目

- **项目**是隔离单元：策略目录、授权数据（project_id 列）、管理台可见范围都按项目切分。
- **租户**是项目内的数据归属维度（tenant_id），用于封禁、资源镜像的多租户场景。
- 一个 Keycloak realm + 一份 JWT 校签公钥，全平台共用。

## 第三部分 · 设计注意事项（正确性约束）

以下每条都是"必须成立、否则出安全或一致性问题"的硬约束。

### 10. 策略文件侧

1. **目录不是命名空间，Cerbos 模块 ID 全局唯一**：资源策略按 `(resource, version, scope)`、派生
   角色集合按 `name` 去重。同名模块写在两个项目目录下 = 同一模块两份定义，加载不确定。
   → 派生集合名必须带项目前缀（`custom_roles_{project}`）；写入前查重（409）。
2. **平台层资源（platform / project_permission）只能在 `platform/` 命名空间**：出现在项目目录
   等于用项目级写权限改平台准入。→ 写入端校验资源层级（422）。
3. **策略文件不含 user_id、不写显式 DENY、不记同步态**：未命中即隐式拒绝；把"谁"放进规则就
   破坏了单一数据源。
4. **策略写入与 DB 提交互为回滚**：先写文件后写库，写库失败回滚文件，杜绝"表里有角色、策略
   里没有"的分叉。

### 11. 授权判定侧

5. **授权有两个正交维度，都要过**：① 模块准入（能不能进这个模块）；② 项目/层级范围（能不能
   操作这个项目、这一层的数据）。**两者必须合成**，缺一即越权（见第四部分 G5–G9）。
6. **模块准入必须按"目标项目里的角色"判定，而非跨项目角色并集**：否则"在 A 项目是管理员"会
   带着管理员权限去操作 B 项目。侧边栏可用并集（展示"能进哪些模块"），但**具体请求**要按该
   请求 project_id 对应的成员角色解析。
7. **封禁是先于一切授权的硬拒绝**：型一封禁（subject_ban）在调 Cerbos 之前查，命中即 deny，
   覆盖 ACL 与角色；按 (tenant, project, principal) 收口。
8. **平台层 ACL 委托只有平台管理员能签发**：平台 ACL 按 project_id IS NULL 被平台判定读取，
   项目管理员若能签发就等于自授平台权限。
9. **fail-closed**：Cerbos 不可达时拒绝（503/deny），绝不回退到本地推断。

### 12. 数据一致性侧

10. **DB 只存事实，展示值现算**：角色的 permissions/policy_synced 是**读取时**从策略解析的投影，
    不落库。
11. **注册表需对账**：`role_definitions` 是策略角色的档案索引，只在策略写入 API 时同步。直接
    落盘种子的项目角色会缺席注册表 → 启动时对全部活跃项目做一次幂等对账。
12. **平台级记录必须平台级**：平台功能 ACL 的 project_id 必须为空；写入端与判定读取端都要前置
    过滤，避免把挂在某项目下的平台授权读成平台权限。

### 13. 可观测侧

13. **request_id == trace_id 全链路复用**：日志必须注入 OTel `trace_id/span_id`（否则 trace 与
    Loki 无法互跳）；日志用 JSON（Loki 可解析字段）；DB/Redis/出站 HTTP 也要埋点，否则调用链
    不完整。

## 第四部分 · 实施踩坑清单（经验积累）

以下是本平台在真实联调中**实际发现并修复**的缺陷，按类型归纳。每条给出"症状 → 根因 → 处置"，
是二次开发时最容易重蹈的坑。缺陷编号与完整验证见 `diagnose_v14`~`v20`。

### 14. 越权类（授权两维度未合成）

| 编号 | 症状 | 根因 | 处置 |
| --- | --- | --- | --- |
| G1 | 项目管理员建出平台级租户 | tenant_routes 缺平台守卫 | 加 `require_platform_permission("tenant_mgmt")` |
| G5 | 项目管理员读到别项目的资源/角色/审计 | 读端点显式传 project_id 时不校验范围（写端点早有、读端点漏）| 新增 `assert_project_scope`，所有读端点显式 project_id 必校验 |
| G6 | 项目管理员经 `/acl/grant` 自授平台权限 → 越权到租户管理 | 平台层 ACL 分支未校验 is_platform_admin | 平台层 grant 要求平台管理员 |
| G7 | 项目管理员经事件重放看到/重发别项目事件 | 重放按全局版本号、无项目过滤 | 重放按 project_id 收口，抽 `_audit_project_conditions` 共用 |
| G8 | 任意项目成员为别项目铸 API Key（跨项目攻陷外部鉴权面）；只读成员删他人 | provisioning 端点只挂 `get_current_admin`（任意成员放行）| provisioning 收口为 `require_project_admin(本项目)`；成员删除补 admin 判定 |
| G9 | 在 A 项目是管理员、在 B 项目是查看者的人，在 B 项目行使管理员权限 | 模块准入用跨项目角色**并集** + 范围只查成员资格 | 模块准入按**目标项目**的成员角色解析（`resolve_platform_permissions(scope_project_id)`）|

**通用教训**：这一整类都是"模块级准入通过、项目级校验缺失"。修单点是打地鼠；正确做法是
**穷举所有端点 + 静态门禁**（见第 17 节）。

### 15. 数据一致性类

| 编号 | 症状 | 根因 | 处置 |
| --- | --- | --- | --- |
| F1/F2 | 多项目自定义角色策略集合名撞车 | 派生集合名未带项目前缀 | `custom_roles_{project}` + 写入查重 |
| F4 | 平台授权挂在项目下被读成平台权限 | 平台 ACL 未强制 project_id 为空 | 写入/读取双侧前置过滤 |
| D1 | 项目角色在权限矩阵可见、角色管理页看不到 | 注册表只在策略写入 API 同步，落盘种子项目从未同步 | 启动幂等对账全部活跃项目 |

### 16. 可观测类

| 编号 | 症状 | 根因 | 处置 |
| --- | --- | --- | --- |
| OBS-1 | Tempo 的 trace 找不到对应 Loki 日志 | 日志不带 trace_id | structlog 处理器注入 OTel trace_id/span_id |
| OBS-2 | 跨系统日志对不上号 | request_id 与 trace_id 各走各的 | 中间件令 request_id = trace_id（回退 UUID）|
| OBS-3 | Loki 无法解析字段 | ConsoleRenderer 非 JSON | `LOG_FORMAT=json` 输出结构化日志 |
| OBS-4 | 链路只到 HTTP+Cerbos | DB/Redis/httpx 未埋点 | 按需启用对应 instrumentor（可选依赖）|

### 17. 结构性防线（把"易漏"变成"漏了就红"）

穷举测试能发现实例，但证明不了未测路径没问题。本平台用**静态门禁测试**固化不变式：

- `tests/test_policy_conventions.py`：平台层不 import 项目派生角色、项目目录不出现平台层资源。
- `tests/test_authz_scope_guard.py`：穷举所有路由，
  ① 触及项目级数据的端点必须带范围/权属强制标记（抓"零守卫"）；
  ② 签名含调用方提交的 project_id（Query/Form）必须有主动校验标记（抓"某分支绕过"）。
  豁免走显式 ALLOWLIST 并注明理由。**该门禁当场又抓出一处人工穷举漏掉的 G5 实例**——这就是
  结构性防线优于人工审查的证明。

新增端点若漏了项目校验，CI 直接红。这是本平台最重要的一条实施经验。

## 第五部分 · 实施流程与运维

### 18. 接入一个新项目

1. 建项目（管理台 `/projects`）：项目 ID 即策略目录名，登记 client_id / audience，签发 API Key
   （仅显示一次）。
2. 写策略（`policies/{project_id}/`）：定义本项目资源类型与动作，类型名加项目前缀；管理台
   `/policies` 上传校验，PDP 自动重载。
3. 选授权模型（ABAC / 静态角色，见第 7 节）。
4. 建角色与授权：`/roles` 建角色定义（自动生成策略文件），`/permissions` 授 ACL / 绑角色，
   `/restrictions` 配封禁。
5. 加项目成员（`project_members`）：管理员据此在项目模式下可见本项目数据。
6. 接 SDK：读 `GET /api/v1/projects/{id}/sdk-config`。
7. 接生命周期端口：资源写路径同步调用 `register`/`retire`，使策略可引用资源属性。
8. 验证：`/playground` 走真实链路模拟判定。

### 19. 变更与事件

授权变更用 **Outbox 模式**：业务事务内 `write_change_log()`（递增 `global_permission_version` +
插 `permission_changes`）→ `commit` 原子提交 → 提交后双通道发布（Redis Pub/Sub 实时 + Stream
持久化）。Redis 不可用时事件已落表，可 `/events/replay` 补消费。

### 20. 观测栈落地

代码侧已就绪（trace_id 落日志、request_id=trace_id、DB/Redis 埋点可选依赖）。运维侧需：
安装 `opentelemetry-instrumentation-{sqlalchemy,redis,httpx}`；部署 OTel Collector→Tempo/Loki/
Prometheus→Grafana；权限服务设 `OTEL_EXPORTER_OTLP_ENDPOINT` + `LOG_FORMAT=json`；Grafana 配
Loki derived field `trace_id`→Tempo、Tempo trace-to-logs→Loki，实现双向互跳。

## 第六部分 · 数据模型速查

| 表 | 性质 | 关键列 |
| --- | --- | --- |
| `role_definitions` | 角色档案索引 | name, parent_keycloak_roles(jsonb), is_system, project_id（**无 permissions**）|
| `role_bindings` | 事实：主体→角色 | principal, role, resource_type/id, project_id, revoked |
| `acl_entries` | 事实：主体→资源动作 | principal, resource_type/id, action, project_id, expires_at, revoked |
| `restrictions` | 事实：封禁 | restriction_type, principal/resource, project_id(非空), removed |
| `permission_changes` | 变更 outbox/审计 | version, event_type, change_detail(jsonb 含 project_id) |
| `projects` / `project_members` / `project_clients` / `project_api_keys` / `project_audiences` | 项目及其接入基础设施 | project_id 维度 |
| `resource_registry` / `mount_registry` | 资源镜像（判定期属性来源）| project_id, retired, owner … |
| `user_cache` | Keycloak 同步的用户档案 | user_id, username, enabled |

## 附：一句话总纲

**把每类数据钉在唯一位置（规则进策略、事实进 DB、决策进 Cerbos），把授权拆成"模块准入 × 项目
范围"两维并强制合成，再用静态门禁保证新代码不破坏这两条——其余都是细节。**
